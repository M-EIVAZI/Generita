# Generita

ASP.NET Core 8 Web API with PostgreSQL, Redis, Serilog, and Seq.

## Service URLs

| Service | URL |
| --- | --- |
| Public backend API | `https://eivazi.qzz.io` |
| Frontend development server | `http://localhost:5173` |
| AI/book-processing service | `https://arsemi.qzz.io` |
| Local Seq dashboard | `http://localhost:5341` |

The backend uses `https://eivazi.qzz.io` when generating public links for books,
covers, and audio files. CORS and successful payment redirects target the local
Vite frontend at `http://localhost:5173`. The local Docker port remains available
at `http://localhost:7161` for development and integration testing only.

## Run everything in Docker

From the repository root:

```bash
cp .env.example .env
# Edit .env and replace the placeholder values.
docker compose up --build
```

Docker Compose reads the PostgreSQL password and optional JWT signing secret and
ZarinPal merchant ID from the ignored `.env` file. In Development, an empty
`JWT_SECRET` uses an ephemeral key generated by the API. Real credentials are
not kept in tracked configuration files.

`Config.yml` is an old optional Cloudflare Tunnel configuration and is not used
for local execution.

Open the local Docker services:

- API Swagger: <http://localhost:7161/swagger>
- API health: <http://localhost:7161/health>
- Seq logs: <http://localhost:5341>
- PostgreSQL: `localhost:5432`
- Redis: `localhost:6379`

The separate book-processing API is not part of this repository. By default,
the API reaches it through `https://arsemi.qzz.io`. Change
`ApplicationUrls__BookProcessorBaseUrl` in `docker-compose.yml` if that service
uses another address.

Stop the containers with:

```bash
docker compose down
```

## Run the API directly

Start only its dependencies:

```bash
cp .env.example .env
# Edit .env and replace the placeholder values.
docker compose up -d postgres redis seq
ConnectionStrings__DefaultConnection="Host=localhost;Port=5432;Database=generita_db;Username=Mahdi;Password=<your-local-password>" \
JwtSettings__Secret="<your-random-secret-of-at-least-32-characters>" \
dotnet run --project src/Generita.Api --launch-profile http
```

The API uses these non-secret application URL defaults in `appsettings.json`:

- Public API URL: `https://eivazi.qzz.io`
- Frontend URL: `http://localhost:5173`
- Book processor: `https://arsemi.qzz.io`
- Seq server: `http://localhost:5341`

The public backend endpoints are:

- Swagger: <https://eivazi.qzz.io/swagger>
- Health check: <https://eivazi.qzz.io/health>
- Home API: <https://eivazi.qzz.io/api/Home>

The Visual Studio `Container (Dockerfile)` profile sends logs to Seq through
`http://host.docker.internal:5341`, because `localhost` inside that container is
the API container itself. The Docker Compose profile uses `http://seq:80` on the
Compose network.

When the API runs in the `Development` environment without
`JwtSettings__Secret`, it generates an in-memory signing key automatically. This
keeps Visual Studio/local startup convenient without committing a credential;
JWTs issued this way become invalid whenever the API restarts. Configure a
persistent secret through user-secrets or an environment variable when needed.

All values can be overridden with ASP.NET Core environment variables. For
example:

```bash
ApplicationUrls__ClientBaseUrl=http://localhost:5173 \
ApplicationUrls__BookProcessorBaseUrl=http://localhost:9000 \
dotnet run --project src/Generita.Api --launch-profile http
```

## Logging

Serilog writes structured logs to both the console and Seq. HTTP requests are
logged once with their status and elapsed time. Every MediatR command and query
logs its kind, request type, duration, and exceptions. Every EF Core SQL command
(including `SELECT`, `INSERT`, `UPDATE`, and `DELETE`) is also sent to Seq. SQL
logs share a `CorrelationId` with the HTTP request and application request logs.
Request payloads and database parameter values are deliberately not logged because
they can contain passwords, tokens, payment data, or uploaded content.

## Redis cache

Successful cached-query values are stored in Redis; `ErrorOr` failures are never
cached. Each query supplies an absolute TTL and `Cache:DefaultExpirationMinutes`
is used as a safe fallback. Cache hits, misses, writes, removals, and Redis
failures are emitted as structured logs and can be filtered in Seq by
`CacheOperation` or `CacheKey`.

The Redis container is intentionally ephemeral and capped at 256 MB with an LRU
eviction policy because Redis is used as a cache, not as the system of record.
If Redis is temporarily unavailable, reads continue through the original query
handler and the API response is returned without caching.

### Verify Redis caching

With the full Docker Compose stack running, execute this from PowerShell in the
repository root:

```powershell
.\scripts\Test-RedisCache.ps1
```

The script removes only the `generita:Home` cache entry, calls `GET /api/Home`
twice, verifies the Redis key and its TTL, compares both responses, and confirms
the expected `Miss -> Set -> Hit` log sequence. To also verify that the API keeps
working while Redis is temporarily unavailable, run:

```powershell
.\scripts\Test-RedisCache.ps1 -TestRedisOutage
```

The outage test stops and starts only the Compose `redis` service. Cache events
can also be inspected in Seq at <http://localhost:5341> with the filter
`CacheKey = 'Home'`.

## Health checks and full integration test

`GET /health` performs real connectivity probes instead of only reporting that
services were registered. It is available publicly at
<https://eivazi.qzz.io/health> and locally at
<http://localhost:7161/health> when the Docker stack is running:

- `postgresql` calls EF Core `CanConnectAsync` against the configured database.
- `redis` writes, reads, and deletes a short-lived probe key through
  `IDistributedCache`.

A healthy response returns HTTP `200` with this structure:

```json
{
  "status": "Healthy",
  "checks": [
    { "name": "postgresql", "status": "Healthy" },
    { "name": "redis", "status": "Healthy" }
  ]
}
```

Run the complete connectivity and cache-flow test from PowerShell:

```powershell
.\scripts\Test-SystemHealth.ps1
```

If Visual Studio starts the API on a dynamic port, pass that address explicitly:

```powershell
.\scripts\Test-SystemHealth.ps1 -ApiBaseUrl http://localhost:32772
```

It first verifies both `/health` checks and then runs the Redis
`Miss -> Set -> Hit` test. The optional outage scenario is available with:

```powershell
.\scripts\Test-SystemHealth.ps1 -TestRedisOutage
```

## Automated tests

The `tests/Generita.Tests` project covers cache serialization, successful and
failed cache results, concurrent request coalescing, invalid cache values, the
Redis health probe, and the configured application URLs. Run it with:

```bash
dotnet test tests/Generita.Tests/Generita.Tests.csproj
```

The `Software validation` GitHub Actions workflow also builds the full Docker
Compose stack, applies EF Core migrations to a disposable PostgreSQL database,
checks PostgreSQL and Redis through `/health`, and verifies the Redis
`Miss -> Set -> Hit` behavior through the public API.
